# 주역 검수·승인·게시 — 관리자 화면과 API 설계 (2026-10-29)

대상: 주역 콘텐츠 768항목(64괘 × [원문 1 + 현대어 1 + 분야 해석 4 + 변효 해석 6]).
원칙: AI는 초안만 쓰고, **승인되어 게시된 문구만** 사용자에게 보인다. 사주·주역 계산 엔진과 기존 관리자 구조는 바꾸지 않고, 관리자 탭 1개와 API 1개를 추가한다.

## 1. 항목과 상태

| 항목 키 | 내용 | 수 |
|---|---|---|
| `classics:N` | 괘사·단전·대상전·효사·소상전 원문(위키문헌) | 64 |
| `modern:N` | 키워드 3개, 괘사·효사 현대어, 핵심 의미 | 64 |
| `pack:N:<분야>` | 종합·재물·커리어·인연 해석(판단 방향, 결론, 행동 처방 등) | 256 |
| `pack:N:line:P` | 변효 의미·주의·확인 조건 | 384 |

상태: `source-imported`(원문, 대조 전) · `draft`(초안) · `reviewed`(승인) · `rejected`(반려) · `stale`(승인 뒤 내용이 바뀜). 게시 여부는 상태와 별개다.

**승인 ≠ 게시.** 승인한 문구는 게시 전에는 사용자에게 보이지 않는다. 게시는 승인된 항목의 "내용 해시"를 묶은 **불변 스냅샷(게시본 v1, v2…)** 이고, 사용자는 최신 게시본에 같은 해시로 들어 있는 문구만 본다.

핵심 안전장치
1. 문구를 고치면 해시가 바뀌어 승인이 `stale`이 되고 게시본에서도 **즉시** 빠진다(재승인·재게시 전까지 비노출).
2. 코드의 초안 파일이 나중에 바뀌어도 이미 승인한 내용은 해시가 달라지므로 자동으로 빠진다.
3. 반려한 항목은 수정하거나 초안으로 되돌리기 전에는 승인할 수 없고, 관리자 미리보기에서도 문장이 나오지 않는다.
4. 롤백은 이전 게시본의 목록으로 **새 버전**을 만든다(이력 삭제 없음). 그때의 해시가 지금 내용과 다르면 해당 항목은 자동 제외된다.
5. 서비스 개방 플래그(`iching:flags`)는 모든 괘의 원문·현대어와 선택한 분야의 해석·변효 해석이 게시본에 있어야만 켤 수 있다(변효에 따라 어느 괘가 쓰일지 모르므로 부분 개방 금지). 이 플래그는 점괘 서비스가 만들어질 때 읽는 값이며 지금은 사용자 화면에 영향이 없다.

## 2. 수정 규칙(저장 전 서버 검사)

- 구조: 키워드 3개, 해야 할 행동 3개·피할 행동 2개, 판단 방향 5종 중 하나, 필수 필드 등.
- 문구: 퍼센트·확정 표현·수익률·구체 날짜, 지양 표현 목록, 반말 어미, 한 항목 안의 같은 문장 반복 → **저장 거부**(422). 전문 용어는 경고.
- 원문(`classics`)은 문구 규칙에서 제외하고 구조만 검사한다.
- 수정본은 코드의 초안을 덮어쓰지 않고 `iching:review:overrides`에 따로 둔다. "수정본 버리기"로 초안으로 돌아간다. 코드 초안이 수정본 이후 바뀌면 화면에 표시한다.

## 3. 저장소(GLOSSARY_KV, 접두어 `iching:`)

| 키 | 내용 |
|---|---|
| `iching:review:state` | `{version, items:{키:{status, contentHash, by, at, note}}}` |
| `iching:review:overrides` | 관리자 수정본 `{키:{content, by, at, baseHash, note}}` |
| `iching:release:current` / `iching:release:v<N>` | 현재 게시본 / 불변 스냅샷 |
| `iching:log:<시각>-<난수>` | 변경 이력(작업·검수자·사유·대상 키) |
| `iching:flags` | 서비스 개방 `{enabled, categories}` |

동시 수정: 모든 쓰기 요청의 `expectVersion`이 저장된 버전과 다르면 409. KV는 원자적 비교-쓰기가 없어 두 요청이 같은 순간 겹치면 뒤의 쓰기가 이길 수 있다(관리자 한두 명 사용을 전제, 모든 쓰기는 이력에 남음). 사용자별 계정이 생기면 Supabase 테이블 + 트랜잭션으로 옮긴다(`_store.js`의 라우팅 접두어에 `iching:`을 추가하면 저장소만 바뀐다).

## 4. API — `/api/iching-review` (관리자 전용, `Authorization: Bearer <관리자 비밀번호>`)

| 메서드 | `a=` | 내용 |
|---|---|---|
| GET | `state` | 상태별 개수, 게시본 정보, 서비스 개방 점검, 플래그 |
| GET | `items` | 목록(유형·상태·괘·분야·검색·페이징 50) |
| GET | `item&key=` | 항목 상세: 현재 내용, 코드 초안, 수정본 정보, 규칙 검사, 출처·판본 차이, 이력 |
| GET | `preview&values=&cat=&mode=&saju=` | 실제 엔진으로 괘를 만들어 8개 섹션 결과 + 스키마·품질 검사. `mode=public`은 **사용자에게 실제 보일 결과(게시본 기준)** |
| GET | `log`, `releases` | 이력, 게시본 목록 |
| POST | `review` | `{action: approve｜reject｜reset, keys[], note, expectVersion}` — 반려는 사유 필수 |
| POST | `edit` / `revert` | 수정 저장(승인 해제) / 수정본 버리기 |
| POST | `publish` | `{dryRun, expectReleaseVersion, expectReviewVersion, note}` — dryRun은 추가·제거·변경·제외 내역만 반환 |
| POST | `rollback` | `{toVersion, expectReleaseVersion, note}` |
| POST | `flags` | 서비스 개방 켜기/끄기(점검 통과해야 켜짐) |

검수자 이름은 `x-reviewer` 헤더(URL 인코딩)로 받아 이력에 `admin:이름`으로 남긴다. 관리자 비밀번호가 하나뿐이라 이름은 **자기 신고**이며 본인 확인이 아니다. 질문 원문·사용자 기록은 이 API가 다루지 않는다.

## 5. 관리자 화면 — 탭 "주역 검수" (AI 풀이 그룹)

1. **요약 카드**: 상태별 개수, 게시본 버전, 서비스 개방 여부·점검, 검수자 이름 입력.
2. **목록**: 유형·상태·괘 번호·검색 필터, 행 클릭으로 상세. "조회 결과 일괄 승인"(현재 페이지의 초안만, 확인창).
3. **상세·편집**: 상태 배지, 원문 출처·저작권·판본 차이, 항목 유형별 편집 폼, 저장(승인 해제)/승인/반려(사유)/초안으로/수정본 버리기, 규칙 검사 결과, 항목 이력.
4. **점괘 미리보기**: 괘·분야·변효 체크(실제 계산) → 8개 섹션 결과, 누락 키, 스키마·품질 검사. "관리자 미리보기(초안 포함)"와 "사용자에게 실제로 보이는 결과" 전환.
5. **게시·롤백·개방**: 게시 점검(dryRun) → 게시(확인창), 게시본 목록과 롤백, 서비스 개방 스위치.
6. **최근 변경 이력**.

## 7. 알려진 한계·결정 필요

- 검수자 계정이 없다(비밀번호 하나, 이름은 자기 신고). 회원·결제와 함께 계정 체계를 정하면 개선한다.
- KV의 동시 쓰기 경합(위 3번). 
- 이 API는 검수·게시 전용이며 사용자용 점괘 API(점괘 생성·기록·권한)는 아직 없다. 서비스 개방 플래그는 그때 읽는다.
- 운영에 배포하려면 Pages Functions 빌드가 `report/iching/*`를 번들하는지(`_iching-runtime.js`의 import) 스테이징에서 확인해야 한다. 로컬에서는 Node로만 검증했다.
- 화면은 로컬에서 임시 서버(인메모리 저장소)로 승인·수정 거부·게시·미리보기까지 확인했고, 실제 관리자 로그인 화면 안의 탭 전환은 확인하지 못했다.

## 8. 사용자 점괘 탭 (만세력 메인 화면 "주역")

- 화면: 루트 `index.html`의 탭 "주역"(타로 다음). 질문 분야 선택 → 질문(선택) → 사주와 함께 보기(선택) → 세 동전 연출(6번 던지기, 효가 아래에서 위로 쌓임) → 결과 8개 카드를 한 단계씩 펼침(원문은 접기). 이전 점괘는 이 기기(localStorage)에만 저장.
- 계산: 브라우저에서 `report/iching/engine.js`(crypto 난수)로 동전 6번 → 효 값 6개를 서버로 전송.
- 해석: `POST /api/iching?a=interpret`(공개) — 서버가 **최신 게시본의 문구만**으로 조합. 서비스 개방 플래그가 꺼져 있으면 403, 필요한 문구가 하나라도 게시되지 않았으면 503(반쪽 해석을 내주지 않음). `GET ?a=status`로 개방 여부 확인, 꺼져 있으면 화면에 "준비 중".
- 사주 연동: 만세력이 이미 계산한 일간·강약·대운(구간별 흐름)을 읽기만 해서 보낸다. 서버는 형식만 검사해 필요한 값만 통과시킨다(다시 계산하거나 고치지 않음).
- 개인정보: 질문·결과를 서버에 저장하지 않고 로그를 남기지 않는다.
- 접근 권한: 개방되면 만세력을 쓰는 누구나 볼 수 있다(회원·결제 시스템이 없어 유료 전용 판정을 아직 하지 않음).
- 파일: `functions/api/iching.js`, `functions/_iching-public.js`, `index.html`(탭·스타일·렌더), `tests/iching-public-sim.cjs`.

## 9. AI 상세 풀이 (사용자가 버튼을 눌렀을 때만, 기본 꺼짐)

목적: 질문 글자를 분석하지 않는 기존 조합 풀이 위에, 질문에 맞춘 구체적인 보충 풀이를 덧붙인다. 기존 원칙(계산에 AI 미사용, AI 문구 자동 게시 금지)은 다음과 같이 지킨다.
- **계산·검수된 풀이는 바꾸지 않는다.** 본괘·변효·변괘는 엔진이 계산하고, AI에는 서버가 게시본으로 다시 만든 결과를 근거로 전달한다(클라이언트가 보낸 결과는 무시). AI는 "보충 풀이"만 쓴다.
- **출력은 검사해서 통과한 것만 보여 준다.** JSON 구조·길이, 확률·확정 표현·날짜·반말·지양 표현, 입력에 없는 다른 괘 이름 언급, 같은 문장 반복, 사주 정보가 없는데 사주 언급 → 하나라도 걸리면 위반 사유를 붙여 1회 재시도, 그래도 실패하면 내주지 않는다(502).
- **화면에서 구분한다.** "AI 작성" 표시와 "관리자가 한 줄씩 검수한 문장은 아닙니다" 안내. AI 풀이는 관리자 검수·게시 대상이 아니다.
- **동의와 고지.** 사용자가 "위 내용에 동의합니다"를 눌러야 버튼이 켜진다. 질문·풀이 내용이 AI 서비스로 전송되고 이름·생년월일·출생지는 보내지 않는다고 고지한다.
- **비용·남용 제한.** 관리자가 켜기/끄기, 하루 전체 횟수, IP당 하루 횟수, 최대 출력 토큰을 정한다(기본: 꺼짐, 200회/일, 5회/IP, 1400토큰). 시도(재시도 포함)마다 센다. 사이트의 기존 AI 설정(최대 요청 비용·단가)을 따르며, 단가를 모르는데 상한이 있으면 호출하지 않는다. IP는 해시로만 센다.
- **저장하지 않는다.** 서버는 질문·응답·IP 원문을 저장하지 않는다(일별 카운터만). AI 풀이는 사용자의 기기(이전 점괘 기록)에만 남는다.
- **게시되지 않은 문구가 필요한 점괘는 AI도 부르지 않는다**(interpret 와 같은 문).
- 공급자: 키가 있으면 OpenAI 우선, 없으면 Anthropic(기존 `generate()` 재사용, 모델은 기존 환경변수·기본값).

API: `POST /api/iching?a=detail`(공개, `consent:true` 필요), `GET/POST /api/iching-review?a=ai`(관리자 설정·사용량). 코드: `report/iching/ai-detail.js`(프롬프트·검증), `functions/_iching-ai.js`, 테스트 `tests/iching-ai-sim.cjs`(가짜 AI).
