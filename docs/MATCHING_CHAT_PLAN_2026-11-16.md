# 운명의 광장 — 인연 매칭·채팅 설계 (5·6단계, 2026-11-16)

사용자 방향(2026-11-16): **글(포스트)보다 사용자 간 매칭과 채팅을 중점**으로 개발한다. 글·모임·운테크는 지금 수준으로 유지하고, 매칭·채팅을 광장의 중심 기능으로 둔다.

## 1. 먼저 정해야 할 것 (개발 전 결정)

## 2. 매칭 흐름

1. **인연 프로필 켜기**(선택, 기본 꺼짐): 성인 본인확인 → 목적(대화·친구·연애) → 보여 줄 정보(닉네임·사진·일주·한 줄 소개·관심사·활동 지역 '시/도'까지) → 원하는 상대(나이대·목적·지역 범위).
2. **오늘의 인연 카드**: 하루 정해진 수(예: 5명)만 보여 준다(무한 스와이프 금지 → 데이트 앱 느낌을 줄이고 '하루 인연'으로).
   - **명리 지표**와 **생활 지표**를 **나눠서** 보여 준다. 명리: 일주끼리의 관계(천간 합·생·극, 일지 합·충), 오행 보완. 생활: 목적·나이대·지역·관심사 겹침.
   - "관계 성공 확률" 같은 표현 금지. "잘 통할 만한 점 / 서로 조심할 점"으로만 말한다. 출생정보 원본은 쓰지 않는다(일주만).
3. **인연 잇기(관심 보내기)**: 짧은 첫 인사(선택) 와 함께. 하루 보낼 수 있는 수 제한.
4. **서로 이으면 → 대화방**(상호 수락일 때만 채팅). 한쪽만 보낸 관심은 상대가 거절·무시하면 조용히 사라진다(거절 알림 없음).
5. **안전**: 차단·신고(채팅 신고 시 최근 대화 일부를 운영자에게 첨부), 연락처·외부 메신저·송금 유도 감지 경고("외부로 옮기자는 대화는 사기일 수 있어요"), 첫 대화 3일간 사진 전송 제한, 미성년 의심 신고 시 즉시 정지.

## 3. 채팅(1차: 서버 경유)

- 표: `cm_match_profiles`(인연 프로필·선호), `cm_likes`(보낸 관심, 상태), `cm_rooms`(대화방: 두 사람, 열림·닫힘), `cm_messages`(방·보낸 사람·본문·시각·읽음), `adult_verifications`(본인확인 결과 요약: 생년·성별·CI 해시·확인 시각).
- API: `/api/community/match/{profile,today,like,inbox}`, `/api/community/chat/{rooms,messages,send,read,leave}`.
- 새 메시지 확인: 대화 화면이 열려 있을 때만 4초 간격, 목록 화면은 20초. 탭이 숨으면 멈춤.
- 금칙어·연락처 감지는 보내기 전에 서버가 검사(막지는 않고 경고 표시 + 3회 이상이면 운영 알림).
- 알림: 새 매칭·새 메시지 → 1차는 광장 안 배지. 이메일·카카오 알림은 2단계 광고 동의와 별개인 '서비스 알림' 동의를 따로 받는다.

## 4. 유료화(6단계, 나중)

- 크레딧 원장(지급·사용 이력, 멱등 키). 예: 오늘의 인연 추가 보기, 관심 보내기 추가, **두 사람 동의 하에 출생정보를 넣는 심층 궁합 리포트**(기존 compat-pair.js 재사용).
- 심층 분석 결제와 권한을 섞지 않는다. 결혼중개업 해당 여부 확인 전에는 유료 매칭 기능을 켜지 않는다.

## 5. 프로필 사진(2026-11-16 구현)

- 기본 = **내 일간 포스터**(관리자 '일간·일주 영상'의 일간 포스터, 10일간 × 남·여). 다른 사람에게는 일간·일주를 공개한 회원만 포스터가 보인다(포스터가 곧 일간을 드러내므로).
- 직접 올리기: 화면에서 256×256 으로 잘라 다시 그려(위치 정보 등 메타데이터 제거) 올림, 300KB 이하, 파일 머리 글자로 형식 확인, R2 무작위 키, 광장 잠금 안쪽에서만 보임. 바꾸면 옛 파일 삭제, 탈퇴하면 삭제, 관리자가 부적절한 사진을 지울 수 있음(감사 로그).
- 남은 일: 일간 포스터 원본이 1600px 이라 아바타로는 무겁다 → 256px 작은 그림을 따로 만들어 두면 좋다. 을목 등 일부 일간은 운영에 포스터가 아직 없어 첫 글자로 보인다.

- 표 6개(`20261116_match_stage5.sql`): `adult_verifications`(출생 연도·성별·CI 해시만) · `cm_match_profiles` · `cm_daily_picks` · `cm_likes` · `cm_rooms` · `cm_messages`. 신고 대상에 message·user 추가, 신고 수 트리거가 메시지 신고를 댓글로 세지 않게 수정. 프로필 사진 칸(`20261116_plaza_avatar.sql`)도 함께 적용 필요

## 8. 6단계 크레딧 구현 결과 (2026-11-16, 운영 DB 적용·배포, 유료 스위치 꺼짐)

- `20261116_credits_stage6.sql`: `cm_credit_ledger`(지급·사용 이력, 추가만, 멱등 키 unique) + DB 함수 `cm_credit_balance`·`cm_credit_spend`(회원별 잠금 → 잔액 확인 → 차감, 같은 키는 한 번만)·`cm_credit_grant`. 서버(service_role)만 실행. 심층 분석 결제 표(commerce_*)는 건드리지 않음. 운영 DB에서 만들었다 되돌리는 점검 통과(지급 중복 1회, 차감 5→2, 같은 요청 재차감 없음, 잔액 부족 거절, 허용 안 된 용도 거절)
- 유료 스위치 KV `plaza:premium` **기본 꺼짐**. 켜려면 관리자가 "유료 켜기" 입력(감사 로그). 꺼져 있으면 화면에 크레딧이 안 보이고 서버도 거절
- 쓰는 곳: 오늘의 인연 더 보기(기본 3명·크레딧 3, 하루 2번, 더 볼 사람이 없으면 차감 안 함) · 하루 잇기 한도(10) 넘으면 크레딧 1로 잇기. 같은 요청 재전송은 한 번만 처리
- 관리자 ⑨ 크레딧·유료: 스위치·가격·테스트/보상 지급(회수 가능)·최근 원장·누적
- 테스트: match-sim 94항목(크레딧 20항목 추가)

### 결제로 크레딧 사기 — 연결 설계(승인 필요: 기존 결제 코드 수정)
1. 상품: 기존 상품 목록(KV `commerce:products`)에 `kind:'credits'`, `credits: N` 상품 추가(가격 0 = 판매 안 함, 관리자가 가격을 넣어야 판매). 예) 10크레딧 / 30크레딧 / 100크레딧
2. 주문(`/api/commerce/order`): credits 상품은 사주 없이 주문(saju_key = 'credits', worlds = []). 회원 로그인 필수
3. 결제 확인(`grantOrder`): credits 상품이면 구매 권한 대신 `cm_credit_grant(user, N, 'purchase', 주문번호, 'order:'+주문번호)` — 결제 확인·웹훅이 두 번 와도 한 번만 지급
4. 환불(`cancelOrder`): 결제 후 7일 이내·지급 크레딧을 하나도 안 썼을 때만 전액 환불(디지털 재화 청약철회 기준), 환불 시 `-N` 기록. 일부 사용은 환불 불가로 안내
5. 법률: 결혼중개업법 해당 여부 자문 전에는 '연애 매칭 유료' 홍보를 하지 않는다. 약관·상품 안내·환불정책에 크레딧 조항 추가

## 9. 크레딧 결제 연결 구현 (2026-11-16, 배포 · 판매 안 함)

- 상품: `cr10`·`cr30`·`cr100`(kind `credits`, 크레딧 수는 코드 `CREDIT_PACKS`, 관리자는 이름·가격·판매 여부만). **가격 0 = 판매 안 함**, 광장 유료 스위치도 켜져 있어야 주문 생성
- 주문(`/api/commerce/order`): 사주 없이 `saju_key='credits'`·`worlds=[]`. 이용 동의·성인 본인확인 필수. 금액은 서버 상품표
- 지급(`grantOrder`): `cm_credit_grant(purchase, 주문번호, 'order:'+주문번호)` — 복귀 확인·웹훅·관리자 다시 주기가 겹쳐도 한 번. 세계 권한·사주 저장은 만들지 않음
- 환불: 고객 바로 환불은 7일 이내·잔액 ≥ 받은 크레딧(하나도 안 씀)일 때만(`creditRefundCheck`). 취소(바로 환불·관리자·포트원 콘솔 취소 웹훅) 시 `revokeOrder` 가 남은 만큼만 회수(마이너스 없음, `'refund:'+주문번호` 한 번)
