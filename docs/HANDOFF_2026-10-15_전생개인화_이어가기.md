## 2. 사용자 의도와 합의

사용자는 무빙툰이 사주 해설을 단순히 잘라 보여주는 수준이라 재미없다고 지적했다.

처음에는 주제별 고정 줄거리 7개에 가장 강한·약한 십성군, 일간 오행, 신강약을 끼워 넣는 단편 모듈을 구현했다. 이후 사용자가 “사주마다 다르게 나오는 게 맞지?”라고 확인했다. 이 방식은 일부 문장만 달라지고 기본 사건·결말은 같다는 점을 설명했다.

사용자는 다음 방향에 동의하고 진행을 지시했다:

1. **전생 한 주제부터** 제대로 개인화한다.
2. **원국 전체의 검수된 해석**을 읽는다.
3. 그 근거를 인물의 욕망·두려움·모순·상대 인물·시련·딜레마·선택·결말로 변환한다.
4. 단편을 집필하고, 근거와 개연성을 독립적으로 검토한다.
5. 통과한 이야기를 저장해 재방문 때 같은 결과를 빠르게 보여준다.
6. 전생 품질을 확인한 다음 다른 주제로 확대한다. 현재 다른 6개 주제를 새 생성 방식으로 확대하지 않았다.

사용자가 추가로 보여준 관리자 이미지 라이브러리도 반영해야 한다:

- 전생 이미지 **50종 = 십성군 5 × 오행 5 × 인물 성별 2**.
- 이미지에 정해진 인물의 직업·시대·의복·일터는 유지한다.
- 동일 이미지가 선택돼도, 목표·사건·적대자·딜레마·반전·결말은 원국 전체 근거를 조합하여 새로 설계한다.
- 주인공 이미지 선택은 사주에 연결된 인물 슬롯이며, 아래의 **안내자 선택**과는 다른 개념이다.

- 최대 78초. OpenAI 후 Anthropic 가용 키 순서로 시도하되 남은 시간 조건을 확인한다.
- 캐시: `ai:past-story:<hash>`에 검토 통과한 plan/story/review만 저장, TTL 30일.
- 키에는 버전·원국·근거 내용·DB 메타·모델 설정이 포함된다. 근거 비활성화·변경 후 이전 캐시를 재사용하지 않게 했다.

## 6. 새 대화에서 할 일 · 우선순위

### A. 운영 실패를 먼저 재현·진단

1. 위 실패 결과와 현재 소스를 읽는다. 기능이 이미 작동한다고 전제하지 않는다.
2. 기획 JSON 검증의 구체적 거부 사유, 제공자별 단계·시간·중단 이유를 안전하게 추적할 수 있게 한다.
   - 이름/생년월일/비밀키를 로그나 사용자 응답에 노출하지 않는다.
   - 관리자용 진단 또는 짧은 보존기간의 내부 실패 기록을 검토한다.
   - plan-rejected가 형식/필드/ID/길이 중 무엇인지 분리한다.
3. 실제 설정된 모델과 호출 성공 여부, 78초 안에 기획 단계만으로 시간을 소모하는 이유를 확인한다.
4. JSON Schema structured output 지원을 기존 generate()가 이미 가지고 있으므로 필요하면 기획/집필/검토에 적용한다.
5. 단계별 시간 예산과 필요시 비동기 작업 구조를 검토한다. 검토를 생략하거나 실패한 원고를 성공으로 바꾸어 해결하지 않는다.

### B. 실제 생성 품질을 검수

1. 가상 사주 한 건으로 기획·집필·독립 검토까지 통과한 결과를 확보한다.
2. 실제 원고를 읽어서 단편 기획안의 구조를 확인한다: 호감형 일상, 구체적 목표, 적대자의 욕망/두려움, 양쪽 대가가 있는 딜레마, 압박, 절정, 사전 단서가 회수되는 반전, 대가와 여운.
3. 동일 이미지 슬롯이지만 원국이 다른 사례를 골라 비교한다. 직업/시대는 유지하되 사건·갈등·결말이 복제되지 않는지 확인한다.
4. 근거와 예외를 원문에 대조한다. 단순히 claim_ids가 붙었다고 맞는 이야기라고 판단하지 않는다.
5. 시각 미상·적은 근거·모델 실패·취소·재시도도 확인한다.

### C. 저장·감상·관리자까지 실제 연결 확인

1. 동일 원국 재요청 시 같은 이야기·캐시 적중 확인.
2. 근거 수정/비활성화·버전 변경 시 캐시 갱신 확인.
3. 사용자 전생 감상에서 기존 50종 이미지 슬롯과 주인공 직업이 맞는지 확인.
4. 관리자 테스트 사주에서 같은 원고를 확인하는지 검증.
5. 준비 화면/취소/오류 안내가 기술적 세부를 사용자에게 노출하지 않는지 확인.

### D. 완료 보고와 확대

- 실제 운영 통과와 읽어본 원고를 근거로 완료 범위를 설명한다.
- 전생 외 6개 주제는 아직 기존 템플릿 방식이라는 점을 명확히 구분한다.
- 전생 품질을 사용자와 확인한 다음 다른 주제로 확대한다. 아직 전 주제 개인화가 완료된 것처럼 보고하지 않는다.

## 7. 작업 보존·배포 주의

- 기존 개인 파일/변경을 건드리지 않는다. 마지막 git status의 기존 untracked:
  - `.claude/settings.local.json`
  - `report/v2/NEXT_PLAN.md`
  - `외부툴_프롬프트/`
- 이 인계 문서 자체도 아직 커밋하지 않았다.
- 운영 원본 이미지·영상·DB를 삭제하거나 초기화하지 않는다.
- 테스트용 규칙을 운영 지식으로 저장하지 않는다.
- `git push origin main`은 운영 자동 배포다. 관련 파일만 정확하게 stage한다.
- 사용자는 매번 확인을 요구하는 것을 원치 않는다. 새 대화에서 작업을 이어가라고 하면 합의 범위 안에서 구현·테스트·배포까지 진행하되 실패/미검증을 사실대로 보고한다.
